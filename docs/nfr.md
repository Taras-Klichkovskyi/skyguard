# Нефункціональні вимоги SkyGuard

Кожна вимога має вимірний критерій і спосіб перевірки. Значення розраховані на масштаб міста (~1,5 тис. укриттів, до 50 тис. одночасних користувачів під час тривоги).

> Чернетка підготовлена разом зі схемою БД; формулювання погоджуються з Т. Ружилою (SG-19) і використовуються в тест-плані SG-22.

## 1. Продуктивність

| ID | Вимога | Критерій | Перевірка |
|---|---|---|---|
| NFR-P1 | Отримання реєстру укриттів у межах вікна мапи | p95 ≤ 300 мс при 200 запитах/с | Навантажувальний тест (Locust / k6) |
| NFR-P2 | Пошук найближчого відкритого укриття | p95 ≤ 500 мс від запиту до відповіді | Навантажувальний тест |
| NFR-P3 | Доставка зміни статусу споживачам (тривожний режим) | ≤ 2 с від `POST` статусу до WebSocket-повідомлення, p95 | Інтеграційний тест з таймером |
| NFR-P4 | Обробка звіту зі статусом, включно з DQ-1…DQ-3 | p95 ≤ 400 мс | Навантажувальний тест |
| NFR-P5 | Перше відображення мапи на мобільному пристрої (4G) | ≤ 3 с | Lighthouse, профіль Mobile |

## 2. Масштабованість

| ID | Вимога | Критерій | Перевірка |
|---|---|---|---|
| NFR-S1 | API без стану сеансу | Будь-який запит обслуговує будь-який екземпляр; сесія лише в JWT | Огляд архітектури; запуск 2 екземплярів за балансувальником |
| NFR-S2 | Пікове навантаження під час тривоги | Витримує 10× штатного навантаження горизонтальним масштабуванням без зміни коду | Навантажувальний тест зі сплеском |
| NFR-S3 | Ріст реєстру | До 20 тис. укриттів без погіршення NFR-P1 | Тест на синтетичних даних |
| NFR-S4 | WebSocket-розсилка | Шлях масштабування: Redis pub/sub між екземплярами (на прототипі — один екземпляр) | Огляд архітектури |
| NFR-S5 | Ріст журналу аудиту | Партиціювання `audit_log` за місяцями при > 10 млн записів | Огляд схеми |

## 3. Доступність (availability)

| ID | Вимога | Критерій | Перевірка |
|---|---|---|---|
| NFR-A1 | Доступність сервісу | Ціль 99,9 % на місяць (≤ 43 хв простою); для прототипу — 99 % | Моніторинг `/health/ready` |
| NFR-A2 | Плавна деградація | Якщо БД недоступна, клієнт показує останній збережений реєстр з позначкою часу, а не порожню мапу | Тест: зупинка БД під час роботи |
| NFR-A3 | Офлайн-режим клієнта | Останній реєстр і мапа району кешуються на пристрої | Ручний тест у режимі «Літак» |
| NFR-A4 | Відновлення після збою | RPO ≤ 15 хв, RTO ≤ 1 год | Щоденний бекап + WAL-архів, тест відновлення |
| NFR-A5 | Перевірки стану | `/health/live` і `/health/ready` для оркестратора | Автотест (реалізовано) |

## 4. Безпека

| ID | Вимога | Критерій | Перевірка |
|---|---|---|---|
| NFR-B1 | Шифрування в каналі | Лише HTTPS / WSS, TLS ≥ 1.2, HSTS | SSL Labs, оцінка ≥ A |
| NFR-B2 | Автентифікація | JWT: access-токен 15 хв, refresh 7 днів; паролі — argon2id | Огляд коду, тест протермінованого токена |
| NFR-B3 | Авторизація | RBAC «заборонено за замовчуванням»; комендант змінює лише закріплене укриття | Тести SG-13 |
| NFR-B4 | Аудит відмов | **Кожна** відповідь `403` записується в `audit_log` з `outcome = DENIED` | Обов'язковий негативний тест SG-13 |
| NFR-B5 | Незмінність аудиту | `UPDATE / DELETE / TRUNCATE` неможливі; підробка виявляється `audit_log_verify()` | Автотести (реалізовано) |
| NFR-B6 | Мінімізація ПДн | IP лише як хеш; геопозиція не зберігається без активної згоди | Огляд схеми і коду |
| NFR-B7 | Згода | Обробка геопозиції лише за активної згоди на ціль; відкликання діє миттєво | Тести SG-22 |
| NFR-B8 | Терміни зберігання | Видалення / анонімізація за правилами retention з SG-2 | Плановий job + тест |
| NFR-B9 | Захист від типових атак | Відповідність OWASP ASVS рівень 1; rate limit на звіти: ≤ 5 / хв на користувача | Сканер OWASP ZAP |
| NFR-B10 | Секрети | Жодних секретів у репозиторії, лише змінні середовища | `.gitignore`, перевірка в CI |
| NFR-B11 | Відповідність нормам | ЗУ «Про захист персональних даних», GDPR, ISO/IEC 27001 (див. SG-2) | Чек-лист |

## 5. Зручність використання

| ID | Вимога | Критерій | Перевірка |
|---|---|---|---|
| NFR-U1 | Швидкий шлях до укриття | Від відкриття застосунку до маршруту до найближчого відкритого укриття — ≤ 2 дії | Юзабіліті-тест, 5 учасників |
| NFR-U2 | Доступність інтерфейсу | WCAG 2.1 рівня AA: контраст, розмір цілей ≥ 44 px, підтримка скрінрідера | axe DevTools |
| NFR-U3 | Мова | Інтерфейс і повідомлення про помилки українською | Ручна перевірка |
| NFR-U4 | Зрозумілі помилки | Відмова DQ пояснює причину («Ви за 150 м від укриття, підійдіть ближче за 100 м») | Тести SG-22 |
| NFR-U5 | Адаптивність | Коректна робота на екранах від 360 px | Ручна перевірка, DevTools |
| NFR-U6 | Прозорість згоди | Згода надається окремо на кожну ціль, без попередньо поставлених галочок; відкликання — 1 дія | Огляд макета SG-5 |

## 6. Підтримуваність

| ID | Вимога | Критерій | Перевірка |
|---|---|---|---|
| NFR-M1 | Модульна структура | Шари `api / models / db / core` розділені; бізнес-правила не в обробниках маршрутів | Огляд коду |
| NFR-M2 | Тестове покриття | ≥ 70 % рядків і гілок пакета `app`; CI падає, якщо нижче | `pytest --cov --cov-fail-under=70` у CI (налаштовано) |
| NFR-M3 | Зміни схеми | Лише через міграції Alembic; `alembic check` у CI ловить розбіжність моделей і БД | CI (налаштовано) |
| NFR-M4 | Документація API | OpenAPI генерується автоматично, доступна на `/docs` | Автотест (реалізовано) |
| NFR-M5 | Запуск з нуля | Новий розробник запускає систему за ≤ 10 хв за README | SG-24 |
| NFR-M6 | Єдиний стиль коду | ruff без помилок як умова злиття PR | CI (налаштовано) |
| NFR-M7 | Журналювання | Структуровані логи з `request_id`, який збігається з `audit_log.request_id` | Огляд коду |
